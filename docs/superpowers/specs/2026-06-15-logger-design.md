# Workout Logger — Design Spec

**Date:** 2026-06-15
**Status:** Approved for planning
**Phase:** 2 (the "logger" promised in the original brief)

## Goal

Turn the read-only program viewer into a tool you actually use mid-workout in the
gym: start a session, log what you really lifted (set by set, in pounds),
auto-time your rests, leave notes for the coach, and finish — with full history so
each lift shows what you did last time next to what the coach prescribed.

## Guiding principle

We are **not** building a blank Strong/Hevy clone. We already have the coach's
prescription for every day. The logger opens **pre-filled with the coach's
exercises and targets**, and you log your *actuals* on top. The reference column
shows two anchors per set — **Coach** (his kg target) and **Last** (your previous
actual) — so divergence and progression are visible at a glance.

## Locked decisions (from brainstorming)

| Decision | Choice |
|---|---|
| **Logging unit** | Enter weight in **lb** (what you load on the bar). Coach kg is reference only. lb is the stored source of truth for logged sets. |
| **Exercise catalog** | Full Strong-style, **bilingual EN/RU**, with body-part/category filters and thumbnails. |
| **History** | **Full history** kept; each set shows a **"Last"** reference; past sessions are browsable. |
| **Coach notes** | **Per-set note** + one **session message to coach** at Finish. |
| **Rest timer** | Auto countdown with **per-lift defaults** (Squat 1:30, Bench 2:30, Deadlift 5:00; others a sane default), **adjustable per set**. Plus an overall **session timer with pause/resume**. |
| **Deferred (out of scope now)** | Supersets, plate-by-plate lb entry helper, social/sharing, Apple Health export. |

## Decomposition — two sub-projects, built in order

The catalog is large enough to stand alone, and the logger depends on it.

- **Spec A — Exercise Catalog**: bilingual reference data + a search/filter picker
  component. Foundation. Built and merged first.
- **Spec B — Session Logger**: start → timer → per-set logging → rest → finish /
  cancel, with history and notes. Consumes A's picker.

Each ships on its own branch + PR (never pushed directly to `main`).

## Spec A — Exercise Catalog

### Storage

A static, read-only `src/data/exercises.json` shipped with the app — same model as
`program.json`. **Not** a database table: it is reference data that changes rarely
and is regenerated by a build script, so it needs no per-user storage or RLS.

### Schema (per entry)

```ts
interface CatalogExercise {
  id: string            // stable slug, e.g. "squat-barbell"
  nameEn: string
  nameRu: string        // falls back to nameEn when wger has no RU translation
  ruIsFallback: boolean // true when nameRu was filled from nameEn (so we can hand-fix later)
  equipment: Equipment  // reuse src/data/types.ts: barbell|dumbbell|machine|cable|bodyweight
  bodyPart: string      // wger category name: "Legs", "Chest", "Back"… (picker filter 1)
  aliasesEn: string[]   // search synonyms
  aliasesRu: string[]
  defaultRestSec: number // seeds the rest timer for this lift
  thumb?: string         // optional; absent for now → equipment/letter avatar fallback
}
```

The two picker filters are **Body Part** (`bodyPart`) and **Equipment** (`equipment`),
matching the reference app. No separate Compound/Isolation dimension — wger does not
provide it and it adds no value to search.

### Sourcing (the real cost, addressed deliberately)

Hand-authoring hundreds of bilingual entries is the expensive part. Instead:

1. **Seed from [wger](https://wger.de)'s open exercise database** — licensed
   **CC-BY-SA 4.0** (commercial use OK with attribution + share-alike). We record
   attribution in the build script header and `README.md`.
2. A build script (`scripts/build-catalog.mjs`, sibling to `parse-program.mjs`)
   pages the public API and writes `src/data/exercises.json`:
   - Endpoint: `https://wger.de/api/v2/exerciseinfo/?format=json&limit=100&offset=N`
     (response `{count, next, results[]}`; page until `next` is null).
   - Each result has `translations[]` (`name`, `aliases`, `language` as a numeric
     id — **EN = 2, RU = 5**), `equipment[]` (`{id,name}`), `category` (`{id,name}`).
   - Map wger equipment names → our `Equipment` enum (Barbell/SZ-Bar→barbell,
     Dumbbell/Kettlebell→dumbbell, Cable→cable, Machine→machine, everything else /
     "none"→bodyweight).
   - **Include every exercise that maps cleanly** (has an EN name + a recognized
     equipment) — no heavy manual curation; "hundreds" is the goal. Dedupe by slug.
   - If a RU translation is missing, set `nameRu = nameEn` and `ruIsFallback = true`;
     the script prints the count + ids of fallback entries so common lifts can be
     hand-fixed later.
   - Confirm the powerlifting comp lifts (back squat, bench, conventional/sumo
     deadlift) are present; add any missing one to a small hand-authored
     `scripts/catalog-extras.json` that the build merges in.
3. `defaultRestSec` by heuristic: name contains squat → 90, bench → 150, deadlift →
   300; else barbell → 180; else 90.
4. **No images bundled in this phase.** `thumb` is omitted; the picker shows an
   equipment-type icon / letter avatar (like the reference app). Real thumbnails are
   a deferred enhancement, avoiding per-image CC-BY-SA attribution overhead now.

### Picker UI (`src/components/exercise-picker.ts`)

A modal/sheet that mirrors the reference screenshot, in our dark theme:

- Search box matching **nameEn + nameRu + aliases** (case- and Cyrillic-aware —
  remember JS `\w`/`\b` do not match Cyrillic; use `[а-яё]` classes).
- Two filter chips: **Body Part** and **Equipment**.
- Alphabetical sections with an A–Z fast-scroll index **including Cyrillic** when
  the UI language is RU.
- **Recents** surfaced at the top (from logged history).
- Returns a `CatalogExercise` (or several, for multi-add) to the caller.

### Tests (A)

- Catalog loads, every entry has both names + a valid `equipment` + `defaultRestSec`.
- No duplicate ids; ids are stable slugs.
- Search matches EN, RU, and aliases; Cyrillic query returns Cyrillic matches.
- Filter by body part / equipment narrows correctly.

## Spec B — Session Logger

### Screen model — one screen, two modes

The logger is a **mode of the existing session screen** (`src/screens/session.ts`),
not a new route.

- **Read-only mode** (today's view) gains one primary CTA: **▶ Start Session**.
- **Logging mode** (while a workout is `active` for that day) replaces the hero/reps
  body with the live logger and a header bar.

### Logging-mode layout

- **Header:** elapsed **session timer** with **⏸ pause / ▶ resume**; **Finish**
  (green) on the right.
- **Per exercise** (coach's prescribed list pre-loaded, in order):
  - Title (EN, RU subtitle) + a ••• menu (remove exercise, replace, add note).
  - Set table columns: **Set · Reference · lb · Reps · ✓**.
    - **Reference** stacks **Coach** (kg target) and **Last** (previous actual).
    - **lb** and **Reps** are numeric inputs (`inputmode="decimal"`, so iOS shows
      the number pad; "next" moves to the next field).
    - ✓ banks the set, highlights the row, and **starts the rest countdown**.
  - **Editable rest bar** between sets: shows the current duration, draggable
    handle + −/+ to change *this set's* rest; seeded from the exercise's
    `defaultRestSec`.
  - **+ Add set** (carries the running rest default) and **swipe / trailing − to
    delete** a set.
  - **Per-set note** affordance (small icon → text field).
- Collapsed cards for the remaining exercises (tap to expand).
- **+ Add Exercise** → opens the Spec A picker (coach-prescribed or anything else).
- **Cancel Workout** → confirm dialog ("All progress will be lost", Cancel /
  Resume), matching the reference.
- **Finish** → optional **message to coach** box, then writes the workout and marks
  the day done.

### Timers

- **Session timer**: counts from `started_at`; pause/resume accumulates paused time
  so `duration_sec` excludes pauses.
- **Rest timer**: per-set countdown from `rest_sec`; visible, adjustable, and
  non-blocking (you can keep logging while it runs). A gentle cue (vibrate /
  highlight) at zero — no audio required.

### Behaviour rules

- **One active workout at a time.** Starting a session while another is `active`
  prompts "resume active workout?" instead of starting a second.
- **Start Session replaces "Mark finished"** as the primary action. The old
  one-tap finish survives in the ••• menu as "just mark done" for days you do not
  want to log in detail.
- **Default reps/weight** pre-fill from the coach target (converted to lb), shown
  as ghost text until you confirm — so an as-prescribed set is one tap.

## Data model & persistence

Two new tables, behind the same storage seam as `progress.ts`, with a localStorage
mirror for offline use, and the **`(auth.jwt() ->> 'sub')::uuid`** RLS pattern this
project requires (newer Supabase signing keys make `auth.uid()` return null — see
`2026-06-13-data-and-sync-design.md`).

```sql
create table workouts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null default (auth.jwt() ->> 'sub')::uuid,
  session_num int,                       -- program day; null for ad-hoc
  started_at timestamptz not null,
  ended_at timestamptz,
  duration_sec int,                      -- excludes paused time
  status text not null,                  -- 'active' | 'finished' | 'cancelled'
  coach_message text,
  created_at timestamptz default now()
);

create table logged_sets (
  id uuid primary key default gen_random_uuid(),
  workout_id uuid not null references workouts(id) on delete cascade,
  exercise_ref text not null,            -- catalog id, or "coach:<order>"
  name_en text not null,                 -- denormalized snapshot…
  name_ru text not null,                 -- …so old logs survive catalog edits
  ord int not null,                      -- exercise order within the workout
  set_index int not null,
  weight_lb numeric,                     -- CANONICAL (what you typed)
  reps int,
  done boolean not null default false,
  rest_sec int,
  note text,
  is_coach_prescribed boolean not null default false
);
```

### Three rules that follow from the locked decisions

1. **lb is the source of truth** for logged sets. Coach targets stay kg in
   `program.json`; we convert kg → lb (existing `kgToLb`) for the reference column
   only. No lossy kg↔lb round-trips on stored data.
2. **"Last" reference** = the most recent **finished** workout for this user that
   contains the same `exercise_ref` (fall back to top set when set indexes differ).
3. **Offline resilience** (gym wifi is unreliable): the active workout is mirrored
   to localStorage on every change and synced to Supabase optimistically. A page
   refresh or dropped connection mid-session never loses logged sets; the sync
   reconciles when back online.

### Relationship to existing `progress`

The current `progress` row remains the fast "this day is done" flag for the list
screen, now linked to the finished `workout` (store `workout_id`). The richer
logged workout supersedes the exercises-snapshot for logged days; the snapshot path
stays for days finished via the ••• "just mark done" fallback.

## Error handling

- All writes are optimistic with the existing `toast()` on failure; localStorage is
  always written first so nothing is lost on a failed network call.
- **XSS:** per-set notes and the coach message are **user-entered** — they MUST be
  rendered with `textContent` / escaped, never interpolated into `innerHTML`
  (the rest of the app uses trusted static data; this is the first user-text sink).
- Catalog/build failures are caught in the build script (like the parser), never at
  runtime.

## Testing

- **A:** catalog shape, no dup ids, EN/RU/alias + Cyrillic search, filters.
- **B (pure logic, unit-tested):** session-timer pause/resume accounting;
  rest-default resolution per lift; coach-kg → reference-lb conversion;
  "Last"-reference selection; localStorage mirror round-trip; note escaping.
- **Plate math, focus/tags, data shape:** existing tests stay green.
- Manual: verify in a real browser at ~390px, zero console errors, and that an
  in-progress workout survives a refresh.

## Skills to keep in sync (per CLAUDE.md discipline)

- New schema types → update `parsing-rules.md` schema section if shared types move.
- New `scripts/build-catalog.mjs` → give it a note in `update-program` or a sibling
  `build-catalog` SKILL, and list it in `CLAUDE.md`.
- New persisted keys / tables → update `2026-06-13-data-and-sync-design.md`.

## Out of scope (deliberately)

Supersets, a plate-by-plate lb entry helper, sharing/social, Apple Health / CSV
export, multi-user/coach dashboards. Revisit after the logger is in daily use.
